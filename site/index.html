Why PrivatePaste

One small container. No cloud relay, no analytics, no third-party requests.

Copy here, paste there

Text, links and images you copy land on the clipboard of your other devices a moment later.

A history you can search

Every clip is kept with the device it came from, so what you copied last Tuesday is one search away.

Private copies stay private

On the desktop apps, copies your password manager marks as private are never uploaded, and you can block other apps too. Android only sends what you share.

Encrypted at rest

The database and stored images are encrypted with a key that only you hold.

For a household or a small team

Everyone signs in with their own name and password. One shared history shows who copied what.

Pin what you reuse

Pinned clips get their own tab on every device and survive clearing and auto-delete.

How it works

Your devices talk to your server, and to nothing else.

  1. You copy something on any signed-in device: text, a link or an image.
  2. The app sends it to your server over HTTPS. The server keeps it in an encrypted database.
  3. Your other devices get it at once over a live connection and put it on their clipboard. A device that was offline catches up when it reconnects.
  4. Everything stays searchable in the history on every device and in the web app, until you delete it or clear it.

Security

What protects your clips, and what doesn't.

  • Encrypted at rest. The database (SQLite3 Multiple Ciphers) and the stored image files are encrypted with PP_DB_KEY, a key only you hold.
  • Not end-to-end encrypted. The server can read your clips, so run it on a machine you trust.
  • HTTPS only. The apps accept only HTTPS servers. Plain HTTP works only for localhost.
  • Hashed passwords. Passwords are hashed with Argon2id, and sign-in is rate-limited per IP.
  • A token per device. Every device has its own token. Sign out a lost one on the People page and it is out at once.
  • No telemetry. No analytics, no third-party requests. The apps send data only to your server.

Deploy it in a few minutes

Runs anywhere that runs containers. The image is ghcr.io/dynamicsninja/privatepaste, for amd64 and arm64.

  1. Create a Compose service

    In your Dokploy project, click Create Service, then Compose. Give it a name, for example privatepaste, and choose Raw as the provider.

  2. Paste the compose file

    Paste this into the editor and save.

    docker-compose.yml
    services:
  privatepaste:
    image: ghcr.io/dynamicsninja/privatepaste:__SERVER_VERSION__
    restart: unless-stopped
    stop_grace_period: 15s
    environment:
      PP_DB_KEY: ${PP_DB_KEY}
      PP_PASSWORD: ${PP_PASSWORD}
    volumes:
      - privatepaste-data:/data
    expose:
      - 8080

volumes:
  privatepaste-data:

  3. Set the environment

    On the Environment tab, paste these two lines and fill them in:

    • PP_DB_KEY: a random key that encrypts everything. Generate one with openssl rand -base64 32.
    • PP_PASSWORD: a strong password you'll sign in with.
    Environment
    PP_DB_KEY=
PP_PASSWORD=

  4. Add your domain

    On the Domains tab, add your hostname for service privatepaste on port 8080, with HTTPS on. Point the hostname's DNS at your Dokploy server.

  5. Deploy and sign in

    Click Deploy. Open your domain and sign in with the name owner and your PP_PASSWORD.

  1. Make a folder

    On a server with Docker and Docker Compose, for example a VPS.

    Shell
    mkdir privatepaste && cd privatepaste

  2. Create docker-compose.yml

    PrivatePaste, with Caddy in front for HTTPS. Caddy gets a certificate for your domain by itself.

    docker-compose.yml
    services:
  privatepaste:
    image: ghcr.io/dynamicsninja/privatepaste:__SERVER_VERSION__
    restart: unless-stopped
    stop_grace_period: 15s
    environment:
      PP_DB_KEY: ${PP_DB_KEY}
      PP_PASSWORD: ${PP_PASSWORD}
    volumes:
      - privatepaste-data:/data
    expose:
      - 8080

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    environment:
      PP_DOMAIN: ${PP_DOMAIN}
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
      - caddy-config:/config
    depends_on:
      - privatepaste

volumes:
  privatepaste-data:
  caddy-data:
  caddy-config:

  3. Create the Caddyfile

    Caddy reads your domain from PP_DOMAIN and passes everything to PrivatePaste.

    Caddyfile
    {$PP_DOMAIN} {
    reverse_proxy privatepaste:8080
}

  4. Create .env with your domain and keys

    Put your domain in the second line. This generates the key that encrypts everything (PP_DB_KEY) and your sign-in password (PP_PASSWORD), then shows the password.

    Shell
    cat > .env <<EOF
PP_DOMAIN=paste.example.com
PP_DB_KEY=$(openssl rand -base64 32)
PP_PASSWORD=$(openssl rand -base64 18)
EOF
grep PP_PASSWORD .env

  5. Point your domain at the server

    Add an A record (and an AAAA record for IPv6) for your domain with the server's address, and open ports 80 and 443 in its firewall.

  6. Start it and sign in

    Shell
    docker compose up -d

    Open your domain with https:// and sign in with the name owner and the password from .env.

Already run Traefik, nginx or another proxy?

Leave out the caddy service and the Caddyfile. Attach privatepaste to your proxy's Docker network (called proxy here; use its real name) and route your domain to port 8080. Don't publish the port: the sign-in rate limit trusts the client IP your proxy forwards, so the server must be reachable only through the proxy.

docker-compose.yml
services:
  privatepaste:
    # ... as above, plus:
    networks:
      - proxy

networks:
  proxy:
    external: true

To upgrade, back up /data, change the image tag to the new version and redeploy. See Backups in the self-hosting guide.

Keep PP_DB_KEY safe, apart from your backups. Without it the data can't be recovered. More settings, backups and proxy notes are in the self-hosting guide.

Then connect your devices

Install an app and sign in with your server's address, the name owner and your password. Add the other people on the web app's People page.

  • Windows

    An installer (MSI) for your user, no admin prompt. It isn't code-signed yet, so SmartScreen asks first: click More info, then Run anyway.

  • macOS, Apple Silicon macOS, Intel

    A zip with the app. It isn't notarized yet: right-click PrivatePaste.app and choose Open.

  • Linux

    A tar.gz for x64. Works best in an X11 session; on Wayland the clipboard and hotkey are limited.

  • Android

    An APK for Android 10 or newer. Download it on the phone, open it and allow Install unknown apps for your browser when Android asks.

  • Web: the web app is built into your server. Open your domain in any modern browser.

All files, and older versions, are on GitHub Releases. More in the desktop and Android guides.

Questions

Is it end-to-end encrypted?

No. Your server stores clips encrypted at rest with PP_DB_KEY, but it can read them while it runs. Run it on a machine you trust.

Is there an iPhone app?

Not yet. On an iPhone or iPad you can use the web app in the browser.

Does it run on a Raspberry Pi?

The image is built for amd64 and arm64, so on a Raspberry Pi it needs a 64-bit OS.

What does it cost?

Nothing. It's free and open source under the MIT licence, with no paid tier. You only pay for the machine you run it on.

How is it different from KDE Connect or the Windows and Apple clipboards?

PrivatePaste runs on a server you own, keeps a searchable history, and works across networks and platforms, the web included. KDE Connect sends from device to device on your local network. The Windows cloud clipboard and Apple's Universal Clipboard go through your Microsoft or Apple account and stay inside their own ecosystems.

What if I lose PP_DB_KEY?

Then the data can't be recovered: everything is encrypted with it. Keep it somewhere safe, for example in a password manager, apart from your backups.
