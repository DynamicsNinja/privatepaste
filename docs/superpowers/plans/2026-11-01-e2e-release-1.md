# End-to-end encryption (release 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every clip (text, link, image) is encrypted on the device with a per-server vault key that never reaches the server. Server, desktop, Android and the web UI all speak protocol 2, and older apps are told to update.

**Architecture:**
- **Shared crypto:** one byte-exact implementation in `PrivatePaste.Protocol`, mirrored in Kotlin and JavaScript and pinned by a shared vector file (`docs/e2e-test-vectors.json`) that all three test suites load.
- **Server:** stores opaque ciphertext plus metadata, gates old apps with 426, and holds only the passphrase-wrapped key.
- **Clients:** decrypt at the network edge, so the rest of each app keeps working with a plaintext `ClipDto` (`Text`, `Width`, `Height` filled in) exactly as today. Encryption happens at upload time, so the local queues keep storing plaintext under their existing local encryption.

**Tech Stack:**
- **.NET 10:** `System.Security.Cryptography` (`AesGcm`, `HKDF`, `HMACSHA256`), Konscious Argon2 (already on the server), SkiaSharp (already in Client.Core), QRCoder (new, desktop).
- **Android:** Kotlin, `javax.crypto`, BouncyCastle `bcprov-jdk18on` for Argon2id, `androidx.exifinterface`, ZXing (`com.journeyapps:zxing-android-embedded`) for scanning and generating QR codes.
- **Browser:** WebCrypto, a vendored `hash-wasm` Argon2id build, a vendored `qrcode-generator`, and Node 22's built-in test runner for the JS vectors.

**Spec:** `docs/superpowers/specs/2026-11-01-e2e-rich-text-files-design.md`. This plan covers section "1. End-to-end encryption" plus the protocol rules that make releases 2 and 3 compatible.

## Global Constraints

- **Algorithms:**
  - **Vault key (VK):** 32 random bytes.
  - **Subkeys:** HKDF-SHA256 with no salt:
    - `encKey`: info `"privatepaste v1 enc"`, 32 bytes;
    - `hashKey`: info `"privatepaste v1 hash"`, 32 bytes;
    - `keyId`: the first 8 bytes of HKDF with info `"privatepaste v1 key id"` (32 bytes), as lowercase hex.
  - **Passphrase:** Argon2id with memory 64 MiB (65536 KiB), 3 iterations, parallelism 1, output 32 bytes, a 16-byte random salt, and the passphrase as UTF-8 after NFC normalization.
  - **Wrapping VK:** AES-256-GCM with a 12-byte random nonce and associated data `"privatepaste v1 vault " + keyId`.
- **Small-item format:** `0x01 || nonce(12) || ciphertext || tag(16)`, AES-256-GCM under `encKey`, with associated data `"privatepaste v1 " + purpose`. Purpose is `payload` or `thumb` (and `blob` is reserved).
- **Blob format:** header `0x02 || noncePrefix(8)`, then chunks of 1 MiB of plaintext (the last may be shorter).
  - Each chunk is `ciphertext || tag`, with nonce `noncePrefix || uint32BE(index)` and associated data `"privatepaste v1 blob" || uint32BE(index) || byte isFinal`.
  - An empty input is one final chunk with an empty plaintext.
- **Handover:** the blob is in small-item format under a one-time key `otk`, with associated data `"privatepaste v1 handover"`. The QR text is `privatepaste:handover?id=<id>&k=<base64url otk, no padding>&kid=<keyId>`. Handovers live for 10 minutes, can be fetched once, and the blob is at most 1 KB.
- **Keyed hash:** the server-visible `hash` = lowercase hex of `HMAC-SHA256(hashKey, UTF-8(ContentHash hex))`. `ContentHash` itself stays unchanged.
- **Payload:** UTF-8 JSON (camelCase, `ProtocolJson.Options`) with optional fields `text`, `width` and `height`. Releases 2 and 3 add more, so readers ignore unknown fields.
- **Protocol gate:**
  - Clients send the header `X-PrivatePaste-Protocol: 2` on every request, including the WebSocket upgrade.
  - The clip, sync, vault, handover and `/ws` endpoints answer **426** with detail `Update PrivatePaste to keep syncing.` without it.
  - `/api/auth/*`, `/api/server-info`, `/health` and the Razor pages aren't gated.
- **Server info:** `GET /api/server-info` (no auth) returns `{"protocol":2,"kinds":["text","link","image"],"limits":{"textKb":<PP_MAX_TEXT_KB>,"imageMb":<PP_MAX_IMAGE_MB>}}`.
- **Passphrase rule:**
  - At least 12 characters, and not in the bundled common-passphrase list. The same list file is shipped on all three platforms.
  - Shown copy: `Use at least 12 characters. A short sentence works well.`
- **Copy:** every message below is exact, and copy is sentence case with no exclamation marks (`DESIGN.md`).
- **Never log** passphrases, VK, `otk`, subkeys, decrypted payloads or the QR text. This extends CLAUDE.md's no-key-logging rule.
- **Only the owner** may set up the vault, change the passphrase, or reset encryption. Non-owners see `Ask the owner to set up encryption.` when no vault exists.
- **Image limits:** clients reject images over 50 megapixels or over the server's `imageMb` before uploading. Thumbnails are PNG and fit 256x256.
- `TreatWarningsAsErrors` is on, so a warning fails the build. Run `dotnet test` from the repo root; for Android, run `./gradlew testDebugUnitTest` in `android/` with JDK 21.
- **Pushing `main` deploys the live server and this release wipes its history.** Don't push to `main`; the owner backs up `/data` first (Task 22).

## Review Focus

1. **Web history XSS:** rows are now rendered by JavaScript from decrypted text. A clip containing `<img src=x onerror=alert(1)>` must show as literal text. Tested in Task 11.
2. **Non-ASCII passphrases:** `Šećer na 5. katu` typed on Windows (NFC) and on an Android keyboard that may produce NFD must unlock the same vault. Tested in Tasks 2, 9 and 15 through an NFD vector.
3. **Queued clips across a key reset:** a device that was offline during a reset holds clips queued under the old key. The server answers 409; the client must relock, clear its queue and stop, not retry forever. Tested in Tasks 13 and 18.
4. **Handover race:** two devices scanning the same code at once; exactly one gets the key. Tested in Task 6.
5. **Plaintext left over from before E2E:** after upgrading, a device's old cache, thumbnails and queue (written by the pre-E2E app) are wiped before the first sync and never uploaded. Tested in Tasks 13 and 18.
